# Shared input engine — Phase 5A

VHSInput is a worker-owned Swift/Accelerate library with no UI, device capture, file I/O, history ownership or renderer dependency. Phase 7 adds a VHSCore dependency for immutable mapping-input contracts. VHSRealtime supplies the C handoff queues. At Phase 5A neither was connected to capture devices or the VST3 probe. Phase 5B now adds standalone adapters/Signal status and meters (see INPUTS.md); production host integration remains Phase 8. Synthetic interleaved/planar equivalence does not certify actual host/device routing.

## Ownership and callback boundary

Create one audio queue and one MIDI queue per producer/consumer pair on a control thread. Each queue is strictly SPSC: one serialized producer, one serialized consumer. Multiple MIDI sources/callback threads must not write the same queue concurrently. Adapters must select or serialize sources outside real-time callbacks, or allocate separate queues. Each instance owns its own queues and engine; there is no shared mutable singleton.

Allocate before callbacks start. Stop and join producers/consumer before destroying their queues. Pointers must be non-null valid handles; buffers must contain the declared samples/bytes. Queues copy data and retain no caller buffer. Producers may call only C push/mark-gap APIs. Push/pop paths use lock-free atomics and bounded copies/loops, with no allocation, disk, locks, retry/spin, Swift, UI, rendering or GPU calls. Queue creation/destruction and Swift DSP methods are not callback safe.

The worker exclusively owns AudioAnalyzer and MIDIInput; call drain from its executor, not the audio callback or UI timer. Those classes deliberately are not Sendable. Publish their value snapshots to UI/control with an appropriate ownership boundary when adapters are implemented. Swift DSP may allocate, including rate changes/reset. No wall-clock real-time deadline or measured capture-to-display latency is claimed here.

## Audio contract

- Float32 mono/stereo, planar or interleaved. Planar right=nil means mono. Adapters choose device channels before this boundary. Supported rates: finite 8,000...192,000 Hz. Do not downmix stereo before analysis: channel powers are averaged independently, preserving anti-phase energy. Peak is the maximum absolute value across both channels.
- The producer accepts 1...8192 frames per call; storage is 64 chunks of up to 512 frames, two channels each (32768 frames at full chunks). Whole blocks reserve capacity atomically and publish together. A 1-frame push still occupies one slot. Oversized/invalid/full pushes reject the entire block, increment a dropped-block counter and advance the discontinuity generation. They never partially enqueue samples.
- sampleTime is the absolute frame index of the first sample in the buffer; negative pre-roll is allowed. Adapters convert their native timestamps explicitly. Every chunk retains its frame index, rate, channels and generation. Integer end-time overflow is rejected.
- Producer mark-gap handles stop, disconnect and seek. The consumer clears signals/window/history on a generation change and skips all older queued chunks. A generation change during a drain invalidates that poll too. Rate/channel change or noncontiguous sampleTime also resets warm-up. Queue drain does at most 64 pops per poll. Call drain after a disconnect to publish the cleared state, even if no more samples arrive.
- Snapshot readiness requires one complete analysis window. Window size is the nearest power of two to rate*2048/44100, clamped 512...8192; hop is N/4. At 44.1 kHz: N=2048, 46.44ms window / 11.61ms hop. At 48 kHz: 42.67ms / 10.67ms. Other supported rates vary roughly 30–64ms per window. Snapshot endSampleTime is exclusive and advances only on a complete hop. Queue scheduling and display time add latency; these window durations are not end-to-end latency measurements.
- RMS/peak use the complete unwindowed N-frame window. A full-scale sine has RMS 1/sqrt(2). Nonfinite samples become zero and are counted in invalidSamples for the current window. Finite samples are bounded to [-8,8] before DSP. RMS/peak/bands exposed to consumers clamp to [0,1]; clipped reports a magnitude greater than 1 in the window. Exactly ±1 is valid full scale.
- Bands: Low [20,250) Hz, Mid [250,2000) Hz, High [2000,Nyquist] Hz. Subtract each channel's mean, apply a periodic Hann window and a double-precision complex Accelerate DFT. Sum bin power with positive-frequency symmetry (Nyquist once), divide by N*sum(window²), average channel power and take sqrt. DC is excluded; RMS still includes DC. Bin centers choose bands, so resolution/leakage near edges and the 20Hz cutoff depend on N/rate; no brick-wall filter claim. A bin-centered isolated sine away from band edges has band RMS matching broadband RMS.
- Transient score per hop: clamp((current raw RMS - previous raw RMS - 0.02)/0.25,0,1). Reset previous RMS to zero at a gap; a loud initial window can be an onset. Sustained tones settle to zero. This is a normalized onset signal, not an onset timestamp or beat tracker. Mapping smoothing is Phase 7.

## MIDI 1.0 contract

Packets carry 1...256 bytes, an explicit frame timestamp and nonnegative sample offset. Queue capacity is 64 packets. The byte parser runs on the worker and retains running status/partial messages across packet boundaries. MIDI real-time bytes may interleave without interrupting partial messages. Reset (FF) clears parser and all state. SysEx and system-common status cancel running status; their payload is ignored. Program change/channel pressure consume one byte; poly pressure/pitch bend consume two but produce no supported event.

Supported events: note on, note off, and 7-bit CC on channels 1...16, note/controller 0...127, normalized data2/127. Velocity-zero note on becomes note off. Events retain the timestamp/offset of their status byte, or first data byte under running status, including when completion arrives in a later packet. Bytes within one packet share its time/offset; this engine does not invent per-byte timing. Host VST3 controller assignments need an explicit event adapter later; they are not assumed to be raw MIDI bytes.

State stores velocity per channel/note and CC per channel/controller. Repeated note-on replaces velocity; one note-off releases that channel/note (no overlapping-note count). Sustain CC is a value only, with no sustain emulation. CC120 and CC123...127 release held notes on that channel; CC121 clears that channel's controllers without inventing note-off events. Omni is default; selecting a channel (1...16) clears parser, notes and controllers. Filtering never retargets events.

A failed/invalid/full packet increments the loss generation. Producer mark-gap uses the same epoch for disconnect/reset. The worker clears all note/controller/parser state on a new generation, skips older packets, and discards the poll's events if loss changes while draining. Packet generations prevent an older retained note-on from replaying on the next poll after a lost note-off. New-generation valid packets can start fresh notes. Polling is bounded to 64 pops and at most 16384 events (single-byte Reset worst case). This favors safe release over replay after loss. Adapters must keep polling on disconnect. Active Sensing timeout, MIDI 2.0, MPE, SysEx, program changes, mappings and persisted MIDI learn are outside this slice.

## Fixtures and references

Tests/VHSInputTests covers calibrated signals, stereo/layout equivalence, warm-up/hops, invalid samples and metadata, format/timeline/generation resets, whole-block capacity rejection, queue wrap and simultaneous producer/consumer access; MIDI fragmented/running status, all channels, channel mode, filtering, malformed/system streams, overflow/disconnect and independent state. These fixtures neither open devices nor modify documents.

Accelerate uses Apple's [complex DFT setup](https://developer.apple.com/documentation/accelerate/vdsp_dft_zop_createsetupd) and [DFT execution](https://developer.apple.com/documentation/accelerate/vdsp_dft_executed), with setup destruction scoped to worker ownership. Supported transform lengths are powers of two. Shared-setup alignment requirements do not apply because each Spectrum creates its own independent setup with previous=nil.
